# lesson30: 欠陥分類と根本原因分析 — 欠陥を種類ごとに分けて再発を防ぐ

## このレッスンで学ぶこと

- 根本原因分析（RCA）の目的と、テストアナリストが使う技法を挙げられるようになる
- 古典的な RCA の限界と、欠陥分類が RCA を効率化する仕組みを説明できるようになる
- 欠陥分類が開発プロセスの改善に役立つ理由と、SDLC 全体で統一して分類すべき理由を説明できるようになる
- 直交欠陥分類・IEEE 1044・重要度ベースの分類・欠陥分類モデルといった分類体系の例を区別できるようになる

## 根本原因分析の目的

**根本原因分析**（RCA）は、欠陥の症状だけでなく、その背後にある根本的な原因を識別し、それに対処するための技法です。品質改善のための構造化されたアプローチを支援し、一番の目的は欠陥の再発を予防することです。類似欠陥の再発の軽減（[lesson29](/lessons/lesson29/)）の 2 つ目のアプローチにあたります。

| 対処の対象 | 例 | 効果 |
|------|------|------|
| 症状 | 「割引が二重に適用される」という故障を直す | その欠陥は消えるが、同じ原因から別の欠陥が生まれる |
| 根本原因 | 「割引ルールの優先順位が要件で決まっていなかった」という原因に対処する | 同じ種類の欠陥が再発しにくくなる |

テストアナリスト（TA）は、欠陥や故障の根本原因を識別するためにさまざまな技法を使います。シラバスが挙げる例は次の 4 つです。

<!-- textlint-disable ja-technical-writing/ja-no-successive-word -->

| 技法 | 仕組み |
|------|------|
| 欠陥分類法 | 欠陥を識別し分類するためのカテゴリーのリストに沿って、欠陥を整理する |
| なぜなぜ分析 | 「なぜ起きたか」を繰り返し問い、症状から原因へさかのぼる |
| 特性要因図 | 結果（故障や欠陥）に影響する要因を枝分かれさせて整理する |
| パレート分析 | 原因や種類ごとの件数を大きい順に並べ、影響の大きい少数に絞る |

<!-- textlint-enable ja-technical-writing/ja-no-successive-word -->

RCA の詳細は、ISTQB の改善プロセス向けシラバス（ISTQB-ITP v1.0）の範囲です。このレッスンで扱うのは、欠陥分類が RCA をどう支援するかです。

## 古典的な RCA の限界

古典的な RCA では、欠陥を解決した後に、その欠陥の専門家がかなり詳細に調査します。1 件ずつ丁寧に調べる方法なので、分析の質は高くなります。

問題は件数です。通常、分析が必要な欠陥は数多くあります。欠陥ごとに予防処置の計画を立てていては、非常に非効率で時間がかかります。

この問題へのアプローチの 1 つが、欠陥を分類し、発生した欠陥の**種類**に対して RCA を実施することです。

```mermaid
flowchart LR
    A[多数の欠陥] --> B[欠陥分類\n種類ごとに分ける] --> C[種類ごとの RCA\n共通の根本原因を探す] --> D[是正措置\n再発を防ぐ]
```

個々の欠陥ではなく、似た特徴を持つ欠陥のグループを分析の単位にするので、分析の回数が減り、1 回の分析で多くの欠陥に効く是正措置を導けます。

## 欠陥分類が RCA を支援する仕組み

欠陥分類は、個々の欠陥が、開発プロセスやテスト対象システムに関する多くの情報を含んでいるという認識に基づいています。1 件の欠陥レポートには、どのフェーズで混入したか、どんな種類の誤りか、どの品質特性に関わるか、といった情報が詰まっています。

欠陥分類を使うと、TA は次のことができます。

- 欠陥から、開発プロセスのさまざまな側面に関する情報を抽出する
- 抽出した情報をプロセス測定指標に変換する
- 開発中にどのようなエラーが起きたかという洞察を得て、プロセス改善に役立てる

欠陥分類は、定量的な欠陥統計と定性的な RCA の間のギャップを埋めます。件数を数えるだけの統計では原因はわからず、1 件ずつの RCA では全体の傾向が見えません。分類は、その両方をつなぐ役割を果たします。

### SDLC 全体で統一して分類する

RCA を効果的に支援するには、欠陥を、初期のテストから本番環境に至るまで SDLC 全体を通して統一的に分類すべきです。コンポーネントテストでは「ロジック誤り」、受け入れテストでは「機能不良」、本番では「障害」と呼び方が変わると、同じ種類の欠陥を集計できず、種類ごとの RCA が成り立ちません。

TA は、所属する組織がソフトウェア欠陥の分類を標準化するのを支援すべきです。標準化によって、開発担当者間や組織間の欠陥に関するコミュニケーションと情報交換が改善し、RCA が容易になります。

## 分類からの RCA の進め方

欠陥分類を使った RCA の流れを、架空の例で追います。社内の経費精算システムで、リリースまでに見つかった欠陥 60 件を、混入したフェーズと欠陥の種類で分類したとします。

::: info 混入フェーズ別の集計
| 混入したフェーズ | 件数 | 多かった種類 |
|------|------|------|
| 要件 | 27 | 要件の曖昧さ（18 件）、要件の抜け（9 件） |
| 設計 | 9 | インターフェースの不整合 |
| コーディング | 21 | 境界条件の誤り（12 件）、例外処理の抜け（9 件） |
| 環境・構成 | 3 | 設定値の誤り |
:::

集計の見方と、そこからの進め方は次のとおりです。

<!-- textlint-disable ja-technical-writing/ja-no-successive-word -->

1. 件数の多い種類に絞る（パレート分析）。要件の曖昧さが 18 件で最多なので、まずここを分析の単位にする
2. その種類の欠陥に共通する根本原因を探す（なぜなぜ分析）。たとえば「曖昧な要件がそのまま設計に渡った。要件レビューで曖昧さを確認する観点がなかった。レビューチェックリストが古く、用語の定義も整備されていなかった」とさかのぼる
3. 根本原因に対する是正措置を提案する。要件レビューのチェックリストに曖昧さの項目を追加する（[lesson28](/lessons/lesson28/)）、要件の用語集を整備する、受け入れ基準の書き方を決める、など
4. 次のリリースで、提案した措置が効果をもたらしたかを評価する（[lesson26](/lessons/lesson26/)）

<!-- textlint-enable ja-technical-writing/ja-no-successive-word -->

この例では、18 件の欠陥を 1 件ずつ分析する代わりに、「要件の曖昧さ」という種類に 1 回の RCA を行い、18 件すべてに効く是正措置を導いています。分類の表と件数は教材の例で、実際の分類体系は次に説明する標準や方法を使って組織ごとに決めます。

## 欠陥分類法の例

シラバスは、欠陥分類法の例を 4 つ挙げています。

| 分類法 | 特徴 |
|------|------|
| **直交欠陥分類**（ODC） | 各欠陥を直交する属性に分類する。直交とは相互に排他的という意味で、1 つの欠陥が 1 つの属性で 2 つの値を同時に取らない。属性は、欠陥がレポートされたときと修正されたときの両方で収集する（Chillarege, 1992） |
| **IEEE 1044** | ソフトウェアの不正を分類するための標準で、故障と欠陥を分類するためのコア属性を提供する（IEEE 1044, 2009） |
| 重要度ベースの分類 | 欠陥の重要度（critical、major、minor、trivial など）に基づいて分類する |
| 欠陥分類モデル | 欠陥分類法の研究に基づくモデル。Beizer（1990）や Catolino ら（2019）のものがある |

ODC の「報告時と修正時の両方で収集する」点は見落としやすい特徴です。報告時には故障の現れ方（どんな操作で何が起きたか）がわかり、修正時には欠陥の種類（何をどう直したか）がわかります。両方をそろえて初めて、プロセスのどこで何が起きたかを読み取れます。

欠陥は、ソフトウェア品質モデルを使って品質特性にマッピングもできます。シラバスが挙げる品質モデルは ISO/IEC 25010（2023）と FURPS モデル（Grady ら, 1987）です。品質特性で分類すると、「性能効率性に関わる欠陥が集中している」のように、第4章の品質特性のテスト（[lesson23](/lessons/lesson23/)）との対応で傾向を読めます。

## TA の関わり

欠陥分類と RCA に対する TA の関わりは、欠陥予防の実践（[lesson26](/lessons/lesson26/)）と地続きです。

| 場面 | TA がすること |
|------|------|
| 欠陥データの収集と評価 | 分類と統計分析ができるように、欠陥に関する詳細なデータを集める |
| 分類の標準化 | 組織が SDLC 全体で統一した分類を使えるように支援する |
| RCA への参加 | 欠陥の種類ごとに根本原因を識別し、是正措置を提案する |
| 効果の評価 | 提案した措置が望ましい効果をもたらしたかを、通常はテストマネージャーと相談しながら評価する |

::: tip 欠陥分類が「できること」と「できないこと」
欠陥分類が RCA にもたらすのは効率です。似た欠陥をまとめて分析するので、少ない回数の RCA で多くの欠陥に対処できます。一方で、分類は個々の欠陥を抽象的なカテゴリーに持ち上げる操作なので、1 件の欠陥をより深く分析して多くの根本原因を発見する、という方向には働きません。また、RCA は実際に発生した欠陥や故障を分析する技法なので、テストで欠陥が見つかる前に行うものでもありません。
:::

## 試験のポイント

<!-- textlint-disable ja-technical-writing/ja-no-successive-word -->

- 欠陥分類が RCA を支援する核心は「個々の欠陥ではなく、似た特徴を持つ欠陥のグループを分析の単位にして効率を上げる」ことで、「より深い分析で多くの根本原因を見つける」「テストの前に RCA ができる」は誤り
- RCA の一番の目的は欠陥の再発予防で、TA が使う技法 4 つ（欠陥分類法・なぜなぜ分析・特性要因図・パレート分析）を想起できるようにする（K2）
- 欠陥分類は定量的な欠陥統計と定性的な RCA のギャップを埋め、SDLC 全体（初期のテストから本番環境まで）で統一して分類する
- ODC は直交（相互に排他的）な属性で分類し、欠陥の報告時と修正時の両方で属性を収集する点が特徴
