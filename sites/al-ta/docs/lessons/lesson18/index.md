# lesson18: セッションベースドテストのテストチャーター — ミッション形式で探索の的を絞る

## このレッスンで学ぶこと

- 経験ベースのテストでテストアナリストが専門知識と経験をどう指針にするかを説明できるようになる
- テストチャーターの役割と、その設計に影響する 3 種類の要素を挙げられるようになる
- 探索する対象・使うリソース・発見したい情報の 3 つの部分からなるミッションを書けるようになる
- テストチャーターに含められる追加情報と、詳細度が柔軟性に与える影響を説明できるようになる
- 状況に合うテストチャーターを、対象・リソース・情報の 3 点で見分けられるようになる

## 経験ベースのテストとテストアナリスト

**経験ベースのテスト**は、テスト担当者の経験・知識・直感をもとに行うテストアプローチです。テストアナリスト（TA）は、経験ベースのテストアプローチと経験ベースのテスト技法を採用して、専門知識と過去の経験をテストの指針にします。

エラー推測・探索的テスト・チェックリストベースドテストの基本と、セッションベースドテストの流れ（テストチャーター、時間枠、デブリーフィング）は FL シラバス 4.4（経験ベースのテスト技法）で学んだとおりです。AL-TA の 3.4 節が扱うのは、そのうちセッションベースドテストとチェックリストベースドテストで TA が作る**ドキュメント**と、クラウドテストです。

| 節 | 扱う内容 | レッスン |
|------|------|------|
| 3.4.1 | セッションベースドテストを支援するテストチャーター | このレッスン |
| 3.4.2 | 経験ベースのテストを支援するチェックリスト | [lesson19](/lessons/lesson19/) |
| 3.4.3 | クラウドテスト | [lesson20](/lessons/lesson20/) |

経験ベースのテスト技法はすべて、受け入れテスト駆動開発（ATDD）のようなコラボレーションベースのテストにも適用できます。コラボレーションベースのテストアプローチは FL シラバス 4.5 で学んだとおりです。

## テストチャーターの役割

**セッションベースドテスト**は、テスト活動をテストセッションとして計画するテストアプローチです。探索的テストをこの形で行うとき、各テストセッションのミッションを示すドキュメントが**テストチャーター**です。

テストチャーターは、テストセッションの範囲と目的のほか、制限・スケジュール・リスクといった情報を概説します。テストのロードマップとして機能し、テストセッションに構造を与えます。

```mermaid
flowchart LR
    C[テストチャーター\nセッションのミッション] --> S[テストセッション\n探索しながら設計と実行]
    S --> L[セッションシート\n結果・質問・観察\nアイデア]
```

テストチャーターには、相反するように見える 2 つの働きがあります。

| 働き | 内容 |
|------|------|
| 集中させる | TA がテストすべき特定の領域やフィーチャーに集中できるようにする |
| 柔軟さを残す | 必要なときには、システムを柔軟に探索できるようにする |

::: warning テストスイートを指定するものではない
テストチャーターは、各テストセッションで実行するテストスイートを指定するものではありません。「テストチャーターにテストケースを列挙する」という選択肢はひっかけです。何を探索するかの方向づけはしますが、実際に何をどう試すかは、セッション中に TA が探索しながら決めます。
:::

## 設計に影響する要素

セッションベースドテストのテストチャーターを作るとき、TA は次の 3 種類の要素を考慮しなければなりません。

| 要素 | 例 |
|------|------|
| 顧客および要件の要素 | 顧客から引き出した要件、ビジネスユースケース、品質要件、ユーザージャーニーマップ（時系列で見たユーザーとシステムの相互作用） |
| プロダクト要素 | 機能フロー、プロダクトの主なゴール、プロダクトのフィーチャー、ソフトウェア設計、インターフェース |
| プロジェクトマネジメント要素 | 時間的制約、プロジェクトの意義、見積もり工数、ビジネス価値 |

状況の説明文からテストチャーターを書くときは、この 3 種類を分類に使って材料を拾います。何が重視されているかは顧客および要件の要素、どのフィーチャーや設計に注目するかはプロダクト要素、どれだけの時間と価値があるかはプロジェクトマネジメント要素です。

## ミッションの書き方

テストチャーターは、テスト目的を記述した**ミッション**と、さまざまな追加情報で構成します。

ミッションの一般的な軽量フォーマットは、Hendrickson（2013）の 3 つの部分からなる形です。

> [target] を探索する／[resources] を用いて／[information] を発見するために

| 部分 | 書くこと | 例 |
|------|------|------|
| [target]（探索する対象） | 何を探索するか | 領域、フィーチャー、リスク、コンポーネント、要件 |
| [resources]（使うリソース） | TA が使うもの | テストデータ、構成、ツール、制限、ヒューリスティック、依存関係 |
| [information]（発見したい情報） | どのタイプの情報を見つけることを狙うか | 品質特性の評価、予想される欠陥のタイプ、標準違反 |

::: tip 3 つの部分はそれぞれ別の問いに答える
対象は「どこを見るか」、リソースは「何を使って見るか」、情報は「何を見つけたいか」です。3 つのうち 1 つでも状況と食い違っていれば、そのテストチャーターは状況に合っていません。試験で複数のテストチャーターを比べるときは、この 3 点を 1 つずつ照合します。
:::

## 追加情報

テストチャーターには、ミッションのほかに次のような追加情報を含められます（Ghazi ら、2017）。これらに限りません。

| 追加情報 | 例 |
|------|------|
| 運営情報 | テストセッションの所要時間、開始日時、テスト担当者名 |
| テスト目的 | テストの動機、テストチャーターのミッション |
| テストスコープ | テスト対象システム内の特定の関心領域、テストレベル、使用するテスト技法、テストのアイデア、終了基準、優先度、テストチャーターがカバーすべき範囲、テストしない内容 |
| 開始基準 | テストセッションを開始するために満たすべき事前条件 |
| プロダクト関連情報 | 定義、データ、コンポーネント間のワークフロー、システムアーキテクチャー |
| 制限 | プロダクトが絶対にやってはならないこと |
| テスト環境の記述 | 使う環境の説明 |
| テストに役立つもの | 既存のデータソース、プロダクト情報、テストツール |
| 履歴情報 | 過去に発見された欠陥（互換性や相互運用性の欠陥など）、既存の異常に言及する未解決の問題、過去のテスト関連の故障パターン |
| 制約とリスク | 使用される規制、規則、標準 |

### セッション中の記録

テストセッション中、TA はテスト結果とともに、質問・観察・将来のテストに関するアイデアを記録します。この記録は**セッションシート**に残します。テストチャーターが「セッションの前に書く計画」、セッションシートが「セッション中に書く記録」です。

### 詳細度と柔軟性のトレードオフ

テストチャーターに含める情報の範囲と詳細さはさまざまで、TA の柔軟性の程度に影響します。

| テストチャーターの書き方 | TA への影響 |
|------|------|
| 一般的なテスト目的だけを定義する | 探索の余地が十分に残る |
| 使用するテスト技法まで指定する | TA が制約される可能性がある |
| 「システムが絶対にできないこと」のような情報を加える | 偽陽性の結果を報告する可能性を下げられる |

詳しく書けば書くほどよい、というわけではありません。探索の自由度を残したい部分と、誤った報告を防ぐために明示したい部分を分けて考えます。

## 例題 1 の題材

スマートフォン向けの電子チケットアプリを題材に、状況からミッションを組み立てます。

::: info 電子チケットアプリの次のイテレーション
イベント会場の入場に使う電子チケットアプリに、通信が切れていても入場用の QR コードを表示できる「オフライン表示」機能を追加します。

- 顧客からは「会場の電波状況が悪くても、購入済みのチケットで確実に入場できること」が最も重要な要件として挙げられている
- QR コードは端末に保存したチケット情報から生成し、会場のリーダーが読み取って入場処理を行う。リーダー側のシミュレーターがテスト環境にある
- チケットの購入と決済の機能は、前のリリースから変更しない
- イテレーションの残りは 3 日で、テスト担当者はアプリの利用経験とドメイン知識が豊富である
- ステージング環境には、購入済みチケットのテストデータ一式がある
:::

## 例題 1 の手順

### 手順 1 要素を 3 種類に分ける

状況の説明文から、テストチャーターの設計に影響する要素を拾います。

| 要素 | 状況から読み取れること |
|------|------|
| 顧客および要件の要素 | 電波状況が悪くても確実に入場できることが最重要の品質要件 |
| プロダクト要素 | オフライン表示が新しいフィーチャー。端末に保存した情報から QR コードを生成し、リーダーと連携する |
| プロジェクトマネジメント要素 | 残り 3 日。購入と決済は変更がないので、そこに時間をかける価値は低い |

### 手順 2 探索する対象を決める

対象は、最重要の要件と新しいフィーチャーが重なるところにします。ここでは「オフライン表示機能」です。購入や決済は変更がないので、今回の対象にはしません。

### 手順 3 使うリソースを決める

状況にあるリソースのうち、対象の探索に必要なものを選びます。

- 機内モードにした iOS と Android の端末（通信が切れた状態を作るための構成）
- ステージング環境の購入済みチケットのテストデータ
- 会場のリーダーのシミュレーター（入場処理まで確かめる依存関係）

### 手順 4 発見したい情報を決める

最重要の要件を脅かす欠陥のタイプを書きます。「通信が切れた状態で QR コードが表示されない、またはリーダーが読み取れない欠陥」です。使用性の問題も同時に拾うなら、それも書き添えます。

### 手順 5 ミッションに組み立てる

> オフライン表示機能を探索する／機内モードにした iOS と Android の端末、ステージング環境の購入済みチケットのテストデータ、リーダーのシミュレーターを用いて／通信が切れた状態で QR コードが表示されない、または読み取れない欠陥を発見するために

ミッションには、次のような追加情報を添えます。

| 追加情報 | この例での内容 |
|------|------|
| 運営情報 | 所要時間 90 分、担当者名 |
| 開始基準 | 端末にチケットを保存済みであること |
| 制限 | 購入前のチケットの QR コードを絶対に表示しないこと |
| 履歴情報 | 前のリリースで QR コードの表示崩れが報告されたこと |

### 検算

書いたミッションの 3 つの部分が、手順 1 の表のどれに根拠を持つかを確かめます。

| 部分 | 根拠になった要素 |
|------|------|
| 対象: オフライン表示機能 | 顧客および要件の要素（最重要の要件）とプロダクト要素（新しいフィーチャー） |
| リソース: 機内モードの端末、テストデータ、シミュレーター | プロダクト要素（QR コードの生成とリーダーとの連携）と、状況にあるテスト環境 |
| 情報: 表示されない、読み取れない欠陥 | 顧客および要件の要素（確実に入場できること） |

3 つとも根拠があり、変更のない購入と決済を対象にしていないので、残り 3 日というプロジェクトマネジメント要素とも整合します。

## 例題 2 の題材

オンライン学習サービスを題材に、複数のテストチャーターから状況に合うものを選びます。

::: info 動画講座プレイヤーの機能追加
オンライン学習サービスの動画講座プレイヤーに、倍速再生と字幕表示を追加します。

- 字幕の表示には、外部ベンダーの実績あるコンポーネントをそのまま組み込む
- ステークホルダーが重視するのは、字幕の読みやすさ（アクセシビリティ）と、既存の再生機能が壊れていないこと
- ステージング環境に、講座の動画と字幕データの一式がある
- テスト担当者は、このサービスの利用経験が豊富である
:::

次の 4 つのテストチャーターのうち、この状況に最も合うものはどれでしょうか。

| 候補 | ミッション |
|------|------|
| A | 字幕表示機能を探索する／本番環境の公開中の講座を用いて／字幕の表示崩れを発見するために |
| B | 動画講座プレイヤー全体を探索する／Chrome を用いて／パフォーマンスの問題を発見するために |
| C | 倍速再生と字幕表示を探索する／ステージング環境の講座データ、複数のブラウザー、画面読み上げソフトを用いて／字幕の読みにくさと既存の再生機能のリグレッションを発見するために |
| D | 字幕コンポーネントの内部処理を探索する／コンポーネントのソースコードを用いて／セキュリティの脆弱性を発見するために |

## 例題 2 の手順

候補ごとに、対象・リソース・情報の 3 点を状況と照合します。

| 候補 | 対象 | リソース | 情報 | 判定 |
|------|------|------|------|------|
| A | 字幕だけで、倍速再生と既存機能が抜けている | 本番環境は、テスト環境として不適切 | 表示崩れだけで、読みやすさを扱っていない | 合わない |
| B | プレイヤー全体で、広すぎる | Chrome 1 つに限定している | パフォーマンスは、重視されている事項ではない | 合わない |
| C | 追加した 2 つの機能 | ステージング環境のデータと、読みやすさを確かめる手段 | 重視されている 2 つの事項に対応する | 合う |
| D | 外部ベンダーの実績あるコンポーネントの内部 | ソースコードは、TA の探索的テストのリソースとして不適切 | セキュリティは、重視されている事項ではない | 合わない |

答えは C です。

A は対象とリソースが、B は対象と情報が、D は 3 点すべてが状況からずれています。「字幕」という語が入っているだけで A や D を選ばないように、3 点を 1 つずつ照合します。

::: tip テストチャーターのよくある欠陥
例題 2 の 3 つの誤りを一般化すると、状況に合わないテストチャーターには次のパターンがあります。

| パターン | 例 |
|------|------|
| 対象が広すぎる、または狭すぎる | システム全体を対象にする。重視されているフィーチャーの一部しか対象にしない |
| 発見したい情報が重視されている事項とずれている | 使用性が重要なのにセキュリティの脆弱性を探す |
| リソースが状況に合わない | 本番環境を使う。用意されているテストデータを使わない |
| 変更のない部分に時間を使う | 前のリリースから変えていない機能を対象にする |
| テストケースを列挙している | ミッションではなく、実行する手順の一覧になっている |

このパターンは、この教材が例題から整理したものです。試験では、状況の説明文にある要素を根拠に判断します。
:::

## 試験のポイント

- K3 で問われるのは「状況からミッションを書く」「複数のテストチャーターから状況に合うものを選ぶ」で、対象・リソース・情報の 3 点を状況の要素（顧客および要件、プロダクト、プロジェクトマネジメント）と 1 つずつ照合する
- テストチャーターはテストセッションのミッションを示すロードマップであり、各セッションで実行するテストスイートを指定するものではない
- 詳細度と柔軟性はトレードオフで、テスト技法まで指定すると TA が制約される一方、「システムが絶対にできないこと」を加えると偽陽性の報告を減らせる
- テストチャーターはセッションの前に書く計画、セッションシートはセッション中の記録（結果、質問、観察、アイデア）で、役割を取り違えない
