# lesson28: レビュー技法の応用 — 5 つの技法の使い分けと指摘の偽陽性の見極め

## このレッスンで学ぶこと

- テストベースのレビューがフェーズ内封じ込めに果たす役割と、レビュー技法を選ぶときの考慮要因を説明できるようになる
- アドホック・チェックリストベースド・シナリオベースド・ロールベースド・パースペクティブベースドの 5 つのレビュー技法の仕組みと注意点を区別できるようになる
- 状況の説明から、最も適切なレビュー技法を選べるようになる
- レビューで出した指摘がテストベースの欠陥なのか偽陽性結果なのかを、根拠をもって判断できるようになる

## テストベースのレビューと TA の役割

十分に定義されたテストベースは、作業成果物の品質を確保し、プロジェクトを成功に導く礎です。テストベースをレビューすると、欠陥を早く見つけて対処でき、欠陥が後続のフェーズへ流出するのを防げます。これがフェーズ内封じ込め（[lesson27](/lessons/lesson27/)）の 2 つ目の方法です。

レビュープロセスの活動（計画、レビューの立ち上げ、個々人のレビュー、共有と分析、修正と報告）と、レビュー種別（非形式的レビュー、ウォークスルー、テクニカルレビュー、インスペクション）は FL シラバス 3.2 で学んだとおりです。

テストアナリスト（TA）がレビュー技法を使うのは、このうち個々人のレビュー（AL-TA シラバスの表記では**個別レビュー**）の活動です。テストベースを 1 人で読み、欠陥を識別する場面で、どう読むかを決める方式が**レビュー技法**です。

### 技法を選ぶときの考慮要因

最も適切なレビュー技法を選ぶと、レビューの効率性と有効性が高まります。選択では、次の要因を考慮します。

| 考慮要因 | 例 |
|------|------|
| レビューのゴール | 受け入れテストを書ける情報がそろっているかを確かめたい |
| プロジェクト目的 | 法規制への適合を証明する必要がある |
| 利用可能なリソース | レビューに割ける時間と人数、レビューアの経験 |
| テストベースのタイプ | ユースケース、要件一覧、画面仕様、アクティビティ図 |
| 関連リスク | 誤りが利用者の安全や金銭に直結するか |
| ビジネスドメイン | 医療、金融、行政、小売 |
| 企業文化 | 形式的な手順が受け入れられるか、個人の裁量を重んじるか |

## 5 つのレビュー技法

シラバスは、TA がよく使う 5 つのレビュー技法を説明しています。名前が似ているので、仕組みと注意点をセットで押さえます。

### アドホックレビュー

**アドホックレビュー**は、構造化されたプロセスを持たず、レビューアが非形式的に行う技法です。

- レビューアには、どのように作業を進めるかのガイダンスがほとんど、またはまったく提供されない
- 準備はほとんど要らず、結果はレビューアのスキルに大きく依存する
- レビューアはテストベースを読み、不正を見つけるたびに文書化する
- マネジメントせずに放置すると、複数のレビューアが同じ不正を報告し、重複した報告が大量に発生する

### チェックリストベースドレビュー

**チェックリストベースドレビュー**は、あらかじめ定義したチェックリストに照らしてテストベースを評価する技法です。チェックリストはレビューアに特定の確認事項を促し、レビューを客観化します。

| 観点 | 内容 |
|------|------|
| チェックリストの種類 | 一般的なものから、品質特性・テスト目的・テストベースのタイプに特化したものまである |
| TA による調整 | テストベースのタイプ、リスクレベル、テスト条件に合わせて調整し、テストベースの最も重要な側面に焦点を当てる |
| 更新 | 過去に見過ごした欠陥を使って定期的に更新し、新たに確認された不正の見落としを防ぐ |
| 限界 | チェックリストはすべてを網羅しないので、TA のチェックは項目に限定されない |

項目に限定されないことで欠陥の検出が最大になり、チェックリストが明確にカバーしていない不正も TA が捉えられます。経験ベースのテストを支援するチェックリストの作り方は [lesson19](/lessons/lesson19/) で扱います。

### シナリオベースドレビュー

**シナリオベースドレビュー**は、プロセスや活動をシミュレーションして不正を識別し、テストベースを洗練する技法です。

- テストベースがユースケースやアクティビティ図のようなシナリオベースの形式のとき、最も効果的である
- レビューアは、作業成果物の予想される使用方法に基づいて「ドライラン」を行う
- シナリオは貴重なガイドラインになるが、レビューアは文書化されたシナリオに制約されず、より多くの不正を見つけるためにシナリオを超えて考える必要もある

### ロールベースドレビュー

**ロールベースドレビュー**は、レビューアに特定の役割や責任を割り当てる技法です。

| 役割の決め方 | 例 |
|------|------|
| エンドユーザーのタイプ | 経験者、未経験者、シニア、子供のユーザー |
| 組織内の役割 | システム管理者、一般ユーザー |

各役割は**ペルソナ**で記述できます。ペルソナは、特定のユーザーグループの特性・ニーズ・目標・嗜好を表すように設計した、具体的だが架空の人物像です。レビューアが役割に基づいて責任を分担すると、各自がテストベースの特定の側面に集中できます。包括的なカバレッジを確保しながら、不正の重複も避けられます。

### パースペクティブベースドリーディング

**パースペクティブベースドリーディング**は、さまざまな視点や観点からテストベースをレビューする技法です。視点の例は、設計者、テスト担当者、マーケティング担当者、システム管理者、エンドユーザーです。個々のレビューがより深くなり、レビューア間で見つける不正の重複が減ります。

この技法には、ほかの技法にない要求が 1 つあります。レビューアは、レビュー対象のテストベースを使って、そこから導出するはずの作業成果物を実際に作ろうとします。テスト担当者の視点なら、要件仕様に基づいて受け入れテストの草案を作り、必要な情報がすべて含まれているかを確かめます。

::: info 用語集での位置づけ
ISTQB 用語集は、パースペクティブベースドリーディングを「ロールベースドレビュー技法のひとつで、チェックリストを使用し、プロトタイプ成果物の作成を伴う」と定義しています。ロールベースドレビューの発展形と考えると位置づけがつかめます。
:::

### 5 つの技法の見分け方

| 技法 | 何に沿って読むか | 決め手になる要素 | 効果と注意点 |
|------|------|------|------|
| アドホックレビュー | 何にも沿わない | 準備がほぼ不要 | スキルに依存し、重複報告が出やすい |
| チェックリストベースドレビュー | チェックリスト | 客観化、調整と更新 | 項目に限定されない |
| シナリオベースドレビュー | シナリオ | ドライラン | シナリオを超えて考える |
| ロールベースドレビュー | ユーザーのタイプや組織内の役割 | ペルソナ、責任の分担 | 包括的なカバレッジと重複の回避 |
| パースペクティブベースドリーディング | 職能の視点 | 導出する作業成果物を作ってみる | より深い個別レビューと重複の減少 |

ロールベースドレビューとパースペクティブベースドリーディングの違いは、「誰になりきるか」と「何を作るか」です。ロールベースドレビューはユーザーのタイプや組織内の役割になりきって読みます。パースペクティブベースドリーディングは設計者やテスト担当者といった職能の視点で読み、その視点で作るはずの作業成果物（設計、テスト）を実際に作ろうとします。

## 例題 1 の題材

技法の選択を練習します。次の 5 つの状況に、それぞれ最も適切なレビュー技法を 1 つ選びます。

| 状況 | 内容 |
|------|------|
| ア | 粗大ごみ回収の予約システムの要件が、ユースケース記述として渡された。予約から回収当日までの流れが利用者の視点で通るかを確かめたい |
| イ | 図書館の蔵書検索アプリの画面仕様をレビューする。利用者は小学生から高齢者まで幅広く、操作に不慣れな人が迷わないかを重点的に見たい |
| ウ | 新人 2 人を含むチームで要件仕様をレビューする。前回のリリースで見逃した「エラーメッセージの文言が未定義」という欠陥を、今回は確実に拾いたい |
| エ | 要件仕様から受け入れテストを書き始める前に、テストを書くのに必要な情報（事前条件、入力、期待結果）が要件にそろっているかを確かめたい |
| オ | 社内向けの小さな管理ツールの変更メモ 1 ページを、締め切りまでの 30 分で、そのツールに詳しい担当者 1 人がざっと確認する |

## 例題 1 の手順

状況から「テストベースのタイプ」「レビューのゴール」「利用可能なリソース」を読み取り、技法の特徴と突き合わせます。

| 状況 | 読み取った要因 | 選ぶ技法 | 根拠 |
|------|------|------|------|
| ア | テストベースがユースケース。ゴールは流れの確認 | シナリオベースドレビュー | シナリオベースの形式で最も効果的で、予想される使用方法のドライランができる |
| イ | ゴールが多様なユーザーのタイプごとの確認 | ロールベースドレビュー | 小学生、高齢者、不慣れな人といったエンドユーザーのタイプをペルソナにして分担できる |
| ウ | リソースに新人が含まれる。ゴールは過去の見逃しの再発防止 | チェックリストベースドレビュー | 見逃した欠陥でチェックリストを更新しておけば、経験の差にかかわらず確認事項が促される |
| エ | ゴールが「テストが書けるか」の確認 | パースペクティブベースドリーディング | テスト担当者の視点で受け入れテストの草案を作り、必要な情報の有無を確かめる技法そのもの |
| オ | リソースが 30 分と 1 人。テストベースが小さく、担当者が詳しい | アドホックレビュー | 準備がほぼ不要で、レビューアのスキルに頼れる状況。1 人なので重複報告の問題も起きない |

::: tip 迷いやすい組み合わせ
状況イで「利用者の視点で読む」からとシナリオベースドレビューを選びたくなります。シナリオベースドレビューはテストベースの**形式**（ユースケース、アクティビティ図）で選ぶ技法です。ユーザーの**タイプ**ごとに見るならロールベースドレビューです。状況エも「テスト担当者という役割」に見えますが、作業成果物を作ってみる点がパースペクティブベースドリーディングの決め手です。
:::

## 偽陽性結果の判断

レビューで出した指摘が、すべてテストベースの欠陥とは限りません。**偽陽性結果**は、テスト対象に欠陥が存在しないのに、欠陥として報告した結果です。

レビューでも同じことが起こります。テストベースに欠陥がないのに、レビューアの読み落としや個人的な好みから「欠陥」として報告してしまう指摘が、レビューにおける偽陽性です。

偽陽性の指摘を放置すると、仕様の作成者が不要な修正を検討する手戻りが起き、レビューの指摘全体への信頼も下がります。TA は指摘を提出する前に、次の順で確かめます。

1. 指摘がテストベースのどの記述に対するものかを特定する
2. テストベースの他の記述（前提条件、ビジネスルール、用語集）と照らし合わせる
3. 「期待されること」と「書かれていること」のずれを、テストベースを根拠に説明できるかを確かめる

3 で根拠がテストベースではなくレビューア自身の想定だけなら、その指摘は偽陽性の可能性が高いと判断します。

## 例題 2 の題材

粗大ごみ回収の予約のユースケースを、シナリオベースドレビューでレビューしたとします。出てきた 4 つの指摘のうち、どれが偽陽性かを判断します。

::: info ユースケース「粗大ごみの回収を予約する」
事前条件: 利用者はログインしている。

| 手順 | 利用者 | システム |
|---|---|---|
| 1 | 住所と品目を入力する | |
| 2 | | 品目ごとの手数料と、選べる回収日を表示する |
| 3 | 回収日を選び、予約を確定する | |
| 4 | | 予約番号を発行し、登録済みのメールアドレスへ送信する |
| 5 | 回収日の 2 日前まで予約を取り消せる | |

関連するビジネスルール:

- 1 回の予約で登録できる品目は 5 点まで
- 手数料は、回収日の当日に手数料シールで支払う
- 利用者登録にはメールアドレスの登録が必須
:::

レビューで出た指摘は次の 4 つです。

| 指摘 | 内容 |
|------|------|
| F1 | 手順 1 で 6 点以上の品目を入力したときの振る舞いが書かれていない |
| F2 | 手順 4 で、メールアドレスを登録していない利用者に予約番号を伝える手段がない |
| F3 | 手順 2 の「選べる回収日」が何日先まで表示されるのかが決まっていない |
| F4 | 手数料をオンラインで決済できるようにすべきである |

## 例題 2 の手順

指摘ごとに、テストベースのどこに対するものかを特定し、他の記述と照らし合わせます。

| 指摘 | 対象の記述 | 照らし合わせた結果 | 判定 |
|------|------|------|------|
| F1 | 手順 1 とビジネスルール「5 点まで」 | 上限のルールはあるが、上限を超えたときの流れ（エラー表示か、入力の拒否か）がユースケースのどこにもない | 欠陥（例外処理の欠落） |
| F2 | 手順 4 と事前条件「ログインしている」 | ビジネスルール「利用者登録にはメールアドレスの登録が必須」により、ログイン済みの利用者は必ずメールアドレスを持つ | **偽陽性**（他の記述の読み落とし） |
| F3 | 手順 2 | 「選べる回収日」の範囲を定める記述がなく、2 週間先までなのか 2 か月先までなのかで実装も期待結果も変わる | 欠陥（曖昧さ） |
| F4 | ビジネスルール「当日に手数料シールで支払う」 | 支払い方法はビジネスルールとして明示的に決められており、指摘は仕様のずれではなくレビューアの要望 | **偽陽性**（仕様の欠陥ではなく変更要求） |

F2 は、ユースケースの手順だけを読んでいると見逃しやすい偽陽性です。テストベース全体（事前条件とビジネスルール）を根拠に照らすと、欠陥ではないとわかります。F4 のような改善の要望は、欠陥レポートとしてではなく変更要求として別に扱うのが適切です。

::: warning シナリオを超えて考えることと偽陽性の違い
シナリオベースドレビューでは、文書化されたシナリオを超えて考えることが推奨されます。F1 と F3 は、シナリオを超えて「上限を超えたら」「何日先まで」と考えたからこそ見つかった本物の欠陥です。シナリオを超えて考えることと、テストベースに根拠のない要望を欠陥として出すこととは別です。見つけた指摘を提出する前に、テストベースに根拠があるかを確かめます。
:::

## 試験のポイント

- K3 で問われるのは「この状況に最も適切な技法はどれか」で、テストベースの形式（ユースケースやアクティビティ図ならシナリオベースド）、ユーザーのタイプ別に見るか（ロールベースド）、作業成果物を作ってみるか（パースペクティブベースド）で見分ける
- チェックリストベースドレビューはチェックリストの項目に限定されず、シナリオベースドレビューはシナリオを超えて考える、という「枠を超える」注意点が両方にある
- アドホックレビューは準備がほぼ不要な代わりにスキルに依存し、マネジメントしないと重複報告が大量に出る
- 偽陽性の判断は、指摘の根拠がテストベース（事前条件・ビジネスルールを含む）にあるか、レビューアの想定や要望だけかで決める
