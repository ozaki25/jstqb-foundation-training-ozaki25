# lesson04: テスト環境要件とテストデータ要件 — テスト実行の前提を要件として書き出す

## このレッスンで学ぶこと

- テスト環境要件をどの分析に基づいて定義するかを説明できるようになる
- テスト環境の構成要素の種類と、各構成要素の要件に含める 5 つの情報を挙げられるようになる
- テスト環境の包括的なニーズと、要件の文書化・レビューの進め方を説明できるようになる
- テストデータ要件の 10 の観点について、例を挙げられるようになる

## テスト設計で決める 2 つの要件

テスト設計の中で、テストアナリスト（TA）はテストケースを設計するだけでなく、テスト実行の前提になる 2 つの要件を定めます（[lesson02](/lessons/lesson02/)）。

- **テスト環境要件**: テストを動かす環境に何が必要かを記述する
- **テストデータ要件**: テスト実行のために準備・払い出しが必要なデータを識別し、用意を依頼する

どちらも「要件」です。実際に環境を構築し、データを投入するのはテスト実装の仕事で、テスト設計ではその要件を文書化します。

## テスト環境要件

### テスト環境の重要性

**テスト環境**は、テストの実行に必要なハードウェア・インスツルメンテーション（動作を監視するための機器や仕組み）・シミュレーター・ソフトウェアツールなどの支援要素を含む環境です。テスト環境は、手動と自動の両方のテスト実行にとって重要な成功要因です。テスト環境をどう実装するかは、次に影響します。

- テスト可能性
- 欠陥検出
- 全体的なテストコスト
- テスト結果の信頼性

テスト環境で合格または不合格になったテストケースは、本番環境で実行しても同じ結果になるべきです。理想的なテスト環境は、堅牢で予測可能で、必要であればテスト自動化フレームワークと統合されています。

### 要件を導く 3 つの分析

TA は、次の分析に基づいて、テスト設計中にテスト環境要件を定義できます。

| 分析する対象 | 要件への影響 |
|------|------|
| テスト条件・テストケース・テストデータ要件 | テスト実行の事前条件が満たされるように、テスト環境を設定し維持するために必要な条件を記述する |
| テストレベルとテストタイプ | テスト環境の柔軟性と、本番環境との類似性の間のトレードオフに影響する |
| コンポーネントやシステムの可用性と独立性 | テストダブル（スタブやドライバーなど）を使う必要があるかを示す |

::: tip 柔軟性と本番類似性のトレードオフ
コンポーネントテストの環境では、テストダブルを差し替えて自由に条件を作れる柔軟さが求められます。受け入れテストの環境では、本番環境にできるだけ近いことが求められます。どちらを優先するかは、テストレベルとテストタイプで決まります。
:::

### 構成要素の種類

テスト環境要件は、テスト環境の**構成要素**を記述します。構成要素は次のような種類に分類できます。

| 種類 | 例 |
|------|------|
| ハードウェア | サーバー、端末、カードリーダーなどの周辺機器 |
| ミドルウェア | データベース管理システム、メッセージキュー |
| ソフトウェア | OS、テスト対象アプリケーション、連携する業務システム |
| 仮想化サービス | 外部サービスを模したサービス仮想化 |
| ネットワーク | 帯域、ネットワーク構成 |
| インターフェース | 外部システムとの API 接続 |
| ツール | テスト実行ツール、テストデータ生成ツール |
| セキュリティ | 証明書、アクセス制御 |
| 構成 | 設定値、フィーチャーフラグ |
| 場所 | テストを行う物理的な場所や施設 |

種類の名前はシラバスのもので、例の列はこの教材で補ったものです。

### 各構成要素に含める 5 つの情報

各構成要素について、要件には次の 5 つの情報を含めるべきです（ISO/IEC/IEEE 29119-3）。

| 情報 | 内容 |
|------|------|
| 一意の識別子 | トレーサビリティのために使う |
| 説明 | 要件どおりに実装できる十分な詳しさで記述する |
| 責任 | 誰がそれを利用可能にする責任を持つかを明示する |
| 必要期間 | いつからいつまで必要かを識別する |
| 忠実度 | 本番環境をどの程度再現しているか、どの程度逸脱しているかの度合い |

通販サイトのシステムテストで、配送業者の荷物追跡 API を呼び出す部分をスタブに置き換える場合を例にすると、要件は次のように書けます。

| 情報 | 記述例 |
|------|------|
| 一意の識別子 | ENV-ST-07 |
| 説明 | 配送業者の荷物追跡 API と同じインターフェース仕様を実装したスタブ。追跡番号に対して「集荷済み」「配達中」「配達完了」「該当なし」の応答をテスト担当者が設定できる |
| 責任 | 開発チームの連携基盤担当が提供し、メンテナンスする |
| 必要期間 | システムテストのテスト実装開始から、受け入れテスト完了まで |
| 忠実度 | 応答の形式と応答コードは本番と同一。応答時間と障害時の振る舞いは再現しない |

::: warning 抜けやすい情報
要件に「何を」「どう振る舞うか」は書いても、「誰が用意するか（責任）」「いつからいつまで必要か（必要期間）」「本番とどこが違うか（忠実度）」は抜けがちです。要件の記述を示して「抜けている情報はどれか」と問う形で出題されやすい点です。
:::

### 環境全体の包括的なニーズ

要件は、個々の構成要素だけでなく、テスト環境全体の包括的なニーズにも対応する必要があります。

- セットアップ
- バックアップとリストア
- セキュリティ要件
- テスト環境を変更できること
- ロールと認可

::: tip 構成要素ごとの情報との区別
バックアップとリストアは環境全体のニーズです。個々の構成要素（荷物追跡 API のスタブなど）の要件に、それぞれのバックアップ手順まで書く必要はありません。
:::

### 文書化とレビュー

TA は、テスト環境要件を明確に、簡潔に、首尾一貫した形で文書化すべきです。図や表も使えます。冗長さや不必要な文書化を避けるために、既存のテスト環境を参照し、そのテストレベルに固有のニーズに焦点を絞れます。

テスト環境要件のレビュー・承認・更新は、関連するステークホルダーも行うべきです。開発担当者、テクニカルテストアナリスト（TTA）、テスト自動化エンジニア、ビジネスアナリスト、スポンサー、プロダクトオーナーなどが該当します。

## テストデータ要件

テスト設計中、TA はテスト実行のために準備や払い出しが必要なテストデータを識別し、用意を依頼します。検討する事項には、目的・形式・利用時のコンテキストが含まれます。テストデータの要件は ISO/IEC/IEEE 29119-3 の 8.5 節にも記載があります。

### 10 の観点

シラバスが重要な点として挙げる観点は次の 10 個です。

| 観点 | 内容 |
|------|------|
| 本番データとの類似性 | 本番データは実世界を反映するが、ばらつきに乏しいことがある。合成データはばらつきをコントロールできる |
| 機密性 | 個人情報などの機密性の高いテストデータは保護が必要。データ保護規制を遵守する |
| 目的 | 事前条件や期待結果を決めるために極めて重要。システムの状態や構成（システムの日時など）、ユーザー権限、データ間の関係にも関わる |
| カバレッジ基準 | 選択したテスト技法のカバレッジ基準に沿ったデータにする。有効なデータに加えて、ネガティブテストのような無効なデータも必要になる |
| データ形式 | API テストのような体系的なデータマネジメントでは、CSV・JSON・XML・データベースなどの構造化データが要件になる |
| トレーサビリティ | テストケースに変更があったときのテストデータの保守性を確保する |
| 保守性 | ローレベルテストケースにテストデータをハードコードしない。テストロジックとテストデータを分離する |
| 依存関係 | 従属データを作るには一連のステップが必要になる |
| 可用性 | 存在しない・アクセスできないサービスはサービス仮想化で再現し、データの欠落に対処する |
| 時間感度とデータの経年変化 | 古いデータや時間の影響を受けやすいデータは、システムの動作に予期しない形や不正確な形で影響する |

### 本番データと合成データ

本番データと合成データには、それぞれ長所と短所があります。

| データ | 長所 | 短所 |
|------|------|------|
| 本番データ | 実世界のデータを反映している | ばらつきに乏しいことがある |
| 合成データ | ばらつきをコントロールできる | 実世界のデータでしか起きない特定の欠陥を見落とすことがある |

合成データは、本番データのパターン・分布・外れ値に関する主要な特徴を反映すべきです。本番データがないシステムでは、合成データが現実的なビジネスシナリオと技術シナリオを反映しなければなりません。**ペルソナ**を使うと、多様なユーザーシナリオと行動を反映したデータを作る指針になります。

### 仮名化と匿名化

機密性の観点では、個人情報を含むテストデータをどう保護するかが問われます。

| 処理 | 内容 |
|------|------|
| 仮名化 | 個人情報を人工的な識別子で置き換える |
| 匿名化 | 個人を識別できる情報を削除する |

必要に応じて、TA は EU の GDPR や米国の HIPAA のようなデータ保護規制を遵守しなければなりません。

::: tip 匿名化データの性質
匿名化データは本番データから作られるので、「本番データとの類似性」で挙げた短所をそのまま受け継ぎます。つまり、徹底したテストに必要なばらつきに乏しいことがあります。
:::

### 要件の書き方の例

通販サイトの「注文確定」機能のテストデータ要件を、観点ごとに書いた例です。

| 観点 | 記述例 |
|------|------|
| 目的 | 注文確定時の在庫引き当てを検証するため、在庫数 0・1・10 の商品を用意する。会員ランク（一般・ゴールド）ごとにユーザーを用意する |
| カバレッジ基準 | 境界値分析に合わせて、注文数量 0・1・99・100 の注文データを用意する（上限 99） |
| 機密性 | 顧客データは本番から仮名化して取り込み、氏名と住所を人工的な値に置き換える |
| 依存関係 | 注文データを作るには、商品・在庫・会員の順にデータを作る必要がある |
| 時間感度とデータの経年変化 | クーポンの有効期限はテスト実行日の前後に設定し、固定日付を使わない |

観点の名前はシラバスのもので、記述例はこの教材のものです。

## 試験のポイント

- 構成要素ごとの要件に含める 5 つの情報（一意の識別子・説明・責任・必要期間・忠実度）を漏れなく想起し、要件の記述から抜けている情報を見つけられるように
- 環境全体の包括的なニーズ（セットアップ・バックアップとリストア・セキュリティ・変更能力・ロールと認可）は、構成要素ごとの情報とは別物
- 仮名化は人工的な識別子への置き換え、匿名化は識別情報の削除で、匿名化データは本番由来のためばらつきに乏しいことがある
- テストデータ要件の 10 の観点は例を挙げられるレベル（K2）で、「保守性」はハードコードを避けてロジックとデータを分離するという意味
