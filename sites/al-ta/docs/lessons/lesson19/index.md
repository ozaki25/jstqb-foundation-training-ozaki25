# lesson19: 経験ベースのテストを支援するチェックリスト — はい／いいえで答えられる項目の作り方

## このレッスンで学ぶこと

- チェックリストが経験ベースのテストにもたらす効果と、作成がテストアナリストの責任になる理由を説明できるようになる
- 範囲と形式の決定、情報収集と項目の定義、構造化という作成の手順を説明できるようになる
- よいチェックリスト項目が満たすべき 8 つの条件と、答え方の形式を挙げられるようになる
- 与えられた項目が条件を満たすかを判定し、満たさない項目を書き直せるようになる
- 状況の変更に合わせて、追加すべき項目と見直すべき項目を選べるようになる

## チェックリストが支援するもの

**チェックリストベースドテスト**は、チェックリストの項目を確認するようにテストケースを設計する経験ベースのテスト技法です。適応性が高く、簡便で、ソフトウェア品質を保証する効果があるため、広く使われています。FL シラバス 4.4.3（チェックリストベースドテスト）で学んだ技法の基本を前提に、このレッスンではテストアナリスト（TA）がチェックリストをどう作るかを扱います（経験ベースのテストの位置づけは [lesson18](/lessons/lesson18/)）。

チェックリストを使うと、TA は次の効果を得られます。

| 効果 | 内容 |
|------|------|
| 見落としの防止 | テストアイテムの既知の重要な側面をすべてカバーし、重要な領域の見落としを防ぐ |
| 一貫性 | テストサイクルの間や、複数の TA の間で一貫したテストになる |
| 集中 | 重要な側面に集中できる |
| 経験の記録 | TA が過去に経験した故障や欠陥の記録になる |
| 想起と着想 | 探索的テストの途中などでアイデアを使い果たしたとき、思い出す手がかりや着想の源になる |
| 時間の節約 | 標準的なチェックリストや仲間が作ったチェックリストを再利用できる。ただし、そのチェックリストがテストアイテムに関連している場合に限る |
| 文書化作業の軽減 | テストケースの文書化に必要な作業を減らせる。要件やソフトウェアが常に変化している場合には大きな財産になる |

チェックリストの作成は、多くの場合 TA の責任です。テストの整理や構造化を助け、ガイドとして役立つため、経験ベースのテストを支援します。ただし、再利用でき、保守でき、明確で、効率的なチェックリストを作るには努力が必要です。

## 作成の手順

シラバスは、経験ベースのテストに適したチェックリストを作る手順を、3 つのステップと、その前後に当てはまる指針で示しています。

```mermaid
flowchart LR
    A[範囲・目的・形式を\n決める] --> B[情報を集めて\n項目を定義する] --> C[論理的なグループに\n構造化する] --> D[継続的に\nレビューして洗練する]
    D -. 新しい発見や教訓を反映 .-> B
```

### 範囲と目的と形式を決める

最初に、チェックリストの範囲・目的・形式を決めます。これらがテストの深さと、要求される詳細レベルに影響するからです。形式は 2 種類あります。

| 形式 | 役割 | 項目の例 |
|------|------|------|
| 実行チェックリスト（read-do） | あるプロセスについて考慮すべき主要な要素を含む | チェックすべき入力フィールドの、具体的な無効入力 |
| 確認するチェックリスト（do-confirm） | 思考プロセスを導く補助として、アプリケーションをさらに調査するための経験ベースのテストアイデアを与える | 検索結果に関連性があるかどうかを確認する |

実行チェックリストは「読んでそのとおりに実行する」ための具体的な項目、確認するチェックリストは「ひととおり試したあとで抜けがないか確かめる」ための観点です。

### 情報を集めて項目を定義する

次に、項目を定義するために必要な情報を集めます。

- 経験豊富な専門家から情報を集める
- 欠陥ライブラリや欠陥分類法（Beizer、1990。Kaner と Falk ら、1999）を閲覧する
- 関連文書をレビューする
- リスク、テストケース、潜在的なシナリオを解析する

集めた情報から項目を書くとき、項目は次の 8 つの条件を満たさなければなりません。

| 条件 | 満たさない項目の例 |
|------|------|
| 明確である | 何を確認するのか読み手によって解釈が分かれる |
| 具体的である | 「正しく動くか」のように、確認する対象や条件が書かれていない |
| 曖昧さがない | 複数の読み方ができる |
| 一貫性がある | 仕様や他の項目と食い違う |
| 関連性がある | テストアイテムや今回の変更と関係がない |
| 保守性がある | 画面の細部に依存しすぎて、少しの変更で項目が無効になる |
| 実行可能である | 確認する手段がない |
| 測定可能である | 確認した結果を合否として記録できない |

さらに、項目には答え方と優先度の決まりがあります。

- 「はい」「いいえ」「該当しない」で答えられる質問として書く
- 重要度・潜在的影響・リスクレベルに基づいて優先度を割り当てる

::: warning ハウツーガイドではない
チェックリストは、包括的なハウツーガイドではありません。専門家のための、迅速でシンプルなツールです。操作手順を 1 つずつ書き込むのではなく、専門家が見れば何を確かめればよいかわかる質問にします。
:::

### 論理的なグループに構造化する

最後に、項目を論理的なグループに分類して、チェックリストを構造化し整理します。分類の基準は、機能エリア、ユーザーの役割、テストレベル、その他の関連する基準です。別々のカテゴリーを作ることは、長いチェックリストに特に有効です。

### テンプレートと標準の利用

可能であれば、テンプレートや標準を使います。業界標準や実績のある実践例に沿った既存のテンプレートや定義済みのチェックリストを使えば、労力を節約できます。

### 継続的なレビュー

チェックリストは決して最終的なものではありません。TA は継続的にレビューし、次のものを反映して洗練させていきます。

- 新しい発見事項
- 優先度の変更
- 他のテスト担当者からのフィードバック
- 以前のテストサイクルから得た教訓

チェックリストを他のテスト担当者と共有すると、一貫性と協調性が促進され、テストアイテムやテスト中に焦点を当てるべき重要な領域をよりよく理解できます。

## 例題 1 の題材

図書館の蔵書予約機能を題材に、チェックリスト項目の良し悪しを判定して、悪い項目を書き直します。

::: info 蔵書予約機能の仕様
- 利用者は書名または著者名で蔵書を検索でき、検索結果の一覧には書名・著者名・貸出状況が表示される
- 貸出中の本には予約を入れられる。予約は 1 人 5 冊までで、6 冊目を予約しようとするとエラーメッセージが表示され、予約は登録されない
- 予約した本が返却されると、返却処理から 10 分以内に利用者へ通知メールが届く
:::

TA は、この機能の経験ベースのシステムテストを導くチェックリストに、次の 5 つの項目を候補として挙げました。

| 項目 | 内容 |
|------|------|
| (a) | 検索結果の一覧に、各蔵書の書名・著者名・貸出状況が表示されるか |
| (b) | 予約機能は正しく動くか |
| (c) | すでに 5 冊を予約している利用者が 6 冊目を予約しようとしたとき、エラーメッセージが表示され、予約が登録されないか |
| (d) | 返却通知のメールは、返却処理から何分後に届くか |
| (e) | 予約の上限に達したとき、予約ボタンが灰色になり、赤い警告アイコンが表示されるか |

## 例題 1 の手順

### 手順 1 答え方の形式を確かめる

まず、「はい」「いいえ」「該当しない」で答えられるかを見ます。(d) は「何分後か」を尋ねているので、この形式で答えられません。この時点で (d) は不適切です。

### 手順 2 8 つの条件に照らす

残りの項目を条件に照らします。形式を満たしていても、条件に反する項目があります。

| 項目 | 判定 | 理由 |
|------|------|------|
| (a) | 適切 | 確認する画面と表示項目が具体的で、表示の有無を合否として記録できる |
| (b) | 不適切 | 「正しく動く」が何を指すか不明で、具体的でも測定可能でもない |
| (c) | 適切 | 条件（5 冊予約済みで 6 冊目）と確認する結果（エラーメッセージと未登録）が具体的で、仕様と一致している |
| (e) | 不適切 | 仕様にはボタンの色や警告アイコンの記述がなく、一貫性がない |

(e) は、はい／いいえで答えられる形で書かれているぶん見落としやすい項目です。確認する内容が仕様に根拠を持つかまで照らします。

### 手順 3 不適切な項目を書き直す

条件を満たさない項目は、捨てるのではなく直します。

| 元の項目 | 書き直した項目 | 直した点 |
|------|------|------|
| (b) 予約機能は正しく動くか | 貸出中の本の詳細画面で予約ボタンを押したとき、その本が利用者の予約一覧に追加されるか | 操作と確認する結果を具体的にした |
| (d) 返却通知のメールは何分後に届くか | 予約した本の返却処理から 10 分以内に、利用者に返却通知メールが届くか | 仕様の時間を条件にして、はい／いいえで答えられる形にした |
| (e) 予約ボタンが灰色になり赤い警告アイコンが表示されるか | 予約の上限に達した利用者が予約しようとしたとき、上限に達した旨のエラーメッセージが表示されるか | 仕様にない表示方法を外し、仕様にある結果に合わせた |

書き直した (e) は (c) とほぼ同じ内容になります。重複する項目は 1 つにまとめます。

::: tip 「該当しない」の使いどころ
「予約が複数ある利用者の返却通知メールに、返却された本の書名が含まれるか」という項目は、予約が 1 冊しかない利用者でテストするときには確かめようがありません。その場合は「該当しない」と答えます。項目を書くときは、状況によって該当しないことがあっても、はい／いいえ／該当しないのどれかで必ず答えられる形にします。
:::

## 例題 2 の題材

モバイルバンキングアプリの振込機能を題材に、変更に合わせてチェックリストを見直します。

::: info 振込機能の変更
前のリリースまで、振込機能のチェックリストで経験ベースのシステムテストを行ってきました。既存の項目の一部は次のとおりです。

| ID | 項目 |
|------|------|
| TRF-01 | 振込金額が口座残高を超えるとき、エラーメッセージが表示されて振込が実行されないか |
| TRF-02 | 1 日の振込合計が 50 万円を超えるとき、エラーメッセージが表示されて振込が実行されないか |
| TRF-03 | 振込の確認画面に、振込先・金額・手数料が表示されるか |

次のリリースでは、1 日の振込上限を 50 万円から 100 万円に変更し、画面の英語表示を追加します。英語表示では、すべてのラベルとボタンの文言を英語にし、金額は英語ロケールの桁区切りで表示します。振込の処理そのものは変更しません。
:::

次の項目のうち、このリリースのチェックリストに追加すべきものはどれでしょうか。

| 候補 | 内容 |
|------|------|
| (a) | 振込金額が口座残高を超えるとき、エラーメッセージが表示されて振込が実行されないか |
| (b) | 1 日の振込合計が 100 万円を超えるとき、エラーメッセージが表示されて振込が実行されないか |
| (c) | 英語表示に切り替えたとき、振込の確認画面のすべてのラベルとボタンが英語で表示されるか |
| (d) | 英語表示のとき、振込の確認画面の応答時間は何秒か |
| (e) | 英語表示のとき、金額が英語ロケールの桁区切りで表示されるか |

## 例題 2 の手順

### 手順 1 今回の変更に関連するかを見る

項目は、テストアイテムと今回の変更に関連していなければなりません。

| 候補 | 変更との関連 |
|------|------|
| (a) | 残高の確認は変更していない。すでに TRF-01 として存在する |
| (b) | 上限の変更に対応する |
| (c) | 英語表示の追加に対応する |
| (d) | 英語表示に対応するが、応答時間の変更は今回の対象ではない |
| (e) | 英語表示の追加（金額の表記）に対応する |

### 手順 2 答え方の形式と条件を見る

(d) は「何秒か」を尋ねていて、はい／いいえ／該当しないで答えられません。(b)・(c)・(e) は、条件と確認する結果が具体的で、仕様と一致しています。この 3 つが状況に合う項目です。

### 手順 3 既存の項目を見直す

追加だけでは終わりません。チェックリストは決して最終的なものではないので、変更によって古くなった項目を見直します。TRF-02 は上限が 50 万円だったときの項目で、このまま残すと仕様と一貫性がなくなります。(b) は新しい項目として足すのではなく、TRF-02 を (b) の内容に更新して扱います。

| 操作 | 項目 |
|------|------|
| 更新する | TRF-02 を「100 万円を超えるとき」に書き換える |
| 追加する | (c) と (e) を、英語表示のグループとして追加する |
| 追加しない | (a) は TRF-01 と重複、(d) は形式を満たさない |

追加した (c) と (e) は、「英語表示」という機能エリアのグループにまとめます。既存の振込処理のグループと分けておくと、英語表示だけを確認したいときに探しやすくなります。

## 試験のポイント

- K3 で問われるのは「項目が条件を満たすか」と「状況に合う項目はどれか」で、最初に「はい／いいえ／該当しない」で答えられる形かを確かめ、次に具体性と仕様との一貫性、そして今回の変更との関連性を照らす
- 8 つの条件（明確・具体的・曖昧さがない・一貫性・関連性・保守性・実行可能・測定可能）と、重要度・潜在的影響・リスクレベルに基づく優先度を想起できるようにする
- 実行チェックリスト（具体的な無効入力など、そのとおりに実行する項目）と確認するチェックリスト（思考を導く観点）の違いと、チェックリストはハウツーガイドではなく専門家のための迅速でシンプルなツールだという位置づけ
- チェックリストは決して最終的なものではなく、新しい発見・優先度の変更・他のテスト担当者のフィードバック・前のサイクルの教訓で洗練し続け、再利用はテストアイテムに関連する場合に限る
